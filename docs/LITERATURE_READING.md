# 文献阅读与笔记整理

## 已实现的使用流程

1. 将 PDF、EPUB、Markdown 或 TXT 放入主机资料库，刷新索引。
2. 打开“文献”，选择原文、研究主题；目的可留空，默认阅读全文。选原文时仅在本机提取题录和文字，不调用模型。
3. 点击“生成全文初稿”后才发送提取文本到配置的模型服务。后台识别小标题并逐节分段处理，任务和每步结果保存在 SQLite，关闭页面不影响主机继续工作。
4. 每篇论文形成五列表格：作者信息、背景/目的/意义、主要方法及结果、讨论、想法。按原文小标题组织，作者讨论和助手分析分开，“想法”留给用户。
5. 点击“逐节阅读”，对照本节原文与整理结果；针对本节提问会创建可持久化的后台问答任务，不把用户的问题套用到其他章节。
6. 配置独立个人 Git 仓库后，初稿完成自动生成详细笔记与主题总表并限定路径提交。未配置仓库时仅保存在任务库，可下载 Markdown 或稍后保存。
7. “保存笔记”中可以编辑自己的想法；保存前校验笔记版本，避免覆盖其他设备刚做的修改。
8. 在“模型与规则”中保存今后要复用的阅读偏好。新任务自动加载新规则版本；已有任务保持固定的规则和阶段提示快照。

所有模型整理都标记为“待核对”，不表示用户已读完或助手已核验全部科学结论。模型输出的引用需要逐字存在于对应来源块；这是可定位性检查，不等于对每个推论的语义证明。

## 接入模型

OpenAI 使用 Responses 适配器；DeepSeek、Kimi 默认使用 Chat Completions 兼容适配器，也可以按服务商实际支持情况调整接口类型。配置明确指定模型名，不自动选择、猜测或切换到另一个服务商。

主机环境变量：

| 服务 | 环境变量 | 默认地址 |
|---|---|---|
| OpenAI | OPENAI_API_KEY | https://api.openai.com/v1 |
| DeepSeek | DEEPSEEK_API_KEY | https://api.deepseek.com |
| Kimi | MOONSHOT_API_KEY | https://api.moonshot.cn/v1 |
| 其他兼容服务 | LITERATURE_API_KEY | 自行配置 |

密钥不保存到浏览器、数据库、示例配置或 Git。网页只保存服务商、模型名、地址、接口类型与输出上限。保存设置不会自动发起模型请求。切换服务商也不会把失败任务自动发到新服务；旧任务继续使用原来的服务快照。

Mac/Linux 在启动服务的同一个终端设置变量（下列为占位值，不是真实密钥）：

```bash
export OPENAI_API_KEY='YOUR_KEY_HERE'
.venv/bin/python -m assistant --config config/local.json
```

Windows PowerShell：

```powershell
$env:OPENAI_API_KEY = 'YOUR_KEY_HERE'
.\.venv\Scripts\python.exe -m assistant --config config/local.json
```

随后在网页“模型与规则”填写账号可用的模型名称。对于计划任务，密钥必须在运行该任务的账户/进程环境中可见；仅在交互终端临时设置的变量不会自动传递给已运行或另行启动的计划任务。不要在源码、命令历史共享或截图中暴露真实密钥。

配置参照 `config/example.json` 的 literature 部分。若模型不支持 JSON 模式，可以关闭请求 JSON 模式；程序仍要求结构化 JSON 并验证字段，不接受截断或引用不符的结果。接口兼容性通过 HTTP 模拟验证；真实服务仍需用你自己的账号、模型和额度实测。

官方接口参考：

- https://developers.openai.com/api/docs/guides/structured-outputs
- https://api-docs.deepseek.com/
- https://platform.kimi.com/docs/get-api-key

## 独立个人仓库

本机配置示例：

```json
{
  "literature": {
    "records_root": "/Users/renhan/Documents/Notes",
    "max_requests": 80,
    "model": {
      "provider": "openai",
      "model": "填写账号可用的模型名",
      "api_mode": "responses",
      "base_url": "https://api.openai.com/v1",
      "json_mode": true,
      "max_output_tokens": 6000
    }
  }
}
```

records_root 必须指向独立 Git 仓库根目录，不能是助手代码仓库或其子目录；程序不自动初始化或重写已有仓库。Windows 请先按 PERSONAL_RECORDS.md 转移同一段个人记录历史，再填写当地路径。测试只使用临时仓库，没有向真实个人笔记自动写入测试产物。

生成结构：

```text
个人仓库/
  文献阅读/
    论文/论文标题-稳定ID.md
    主题/主题名-摘要.md
```

详细笔记是规范记录，主题表是由结构化结果与个人想法生成的比较视图。同一论文可以出现在多个主题。当前重新保存某个主题时更新该主题表，其他主题的投影不会实时联动；需在对应主题重新保存。

助手生成区域有明确标记，只更新该区域。用户可在区域外添加手写笔记，“我的想法”有独立区域。若用户在 Obsidian 修改了助手生成区域，程序拒绝覆盖，要求核对；不会把改动悄悄抹去。缺少或重复标记也会拒绝更新。

Git 仅提交本次生成的两份文件。若仓库已有其他暂存修改，会在写文件前拒绝；提交失败时保留已保存文件并报告 `version_pending`。不要把“笔记写入成功”误当作“Git 提交成功”。当前待提交状态需要手动核查并提交/取消暂存后再保存，不做强制清锁或硬重置。

文件写入、数据库、Git 不是跨资源原子事务。程序预先检查所有已知冲突、单文件采用原子替换；崩溃或外部进程并发修改时仍需核对。不要同时在两台主机自动提交同一个同步工作区。

## 阅读流程与 best practice

- 先核对题录和原文版本，区分预印本、正式版本及缺失的补充材料。
- 阅读目的可变，但默认处理整篇可提取文本，不能把只读摘要标为全文阅读。
- 按原文小标题建立论证地图：问题、方法与关键对照、观察结果、作者解释、局限。
- 对关键结论保留页/章/行与短摘录；阅读图像和公式时回到原 PDF 核验。
- 作者观点、助手推测、你的想法分开记录，待核对状态不自动升级。
- 同一原文版本、主题、目的、模型和规则匹配时复用结果；纠正形成新规则版本，不篡改旧任务证据。

阅读方法参考 S. Keshav 的 How to Read a Paper，但不强制用户必须先筛读；本项目按用户要求默认生成全篇初稿，再保留逐节阅读入口。

- https://systems.cs.columbia.edu/ds2-class/papers/keshav-paper.pdf
- https://www.zotero.org/support/adding_items_to_zotero

## 边界与任务恢复

- 只处理文字。PDF 图片、二维公式、复杂表格和多栏顺序未做视觉核验；扫描件需要后续 OCR。EPUB 当前提取正文，不保留插图和出版版式。
- PDF 小标题由模型候选与来源位置校验结合识别；文字包含标题不等于版式已确认。无法识别时标记开篇/未识别，不伪造论文章节。
- 文件大于 80MB 或文字大于 50 万字符会明确拒绝，不会静默截断。单任务最多 80 次已通过验证的模型步骤（配置上限 200）；长文超过上限会保留已完成结果并失败，需拆分。
- 失败不会自动无限重试；用户点击继续后复用已保存步骤。输出/引用未通过验证时该步骤不会成为成功检查点。
- 取消不会撤销已经发出的模型请求，可能仍计费；请求完成后才释放 Worker 所有权。
- 一个本地数据库只运行一个阅读 Worker，使用本机文件锁；不支持数据库放网络盘或多个 uvicorn Worker 的部署方式。
- 重启恢复原模型、原文与规则快照。请求返回但检查点尚未保存时进程中断，恢复可能重复该请求并再次计费；不能承诺外部模型调用 exactly-once。
- 阅读偏好目前由运行库维护版本，通用默认流程和约束由代码 Git 管理。通用“从任意成功任务自动提炼候选能力”、规则导出到 Git、语义能力匹配和规则评测平台仍未实现。
- 当前未接入联网补文献、自动全文下载、OCR、视觉模型或引用格式管理。不能把模型生成的题录当作已联网核验的出版信息。
